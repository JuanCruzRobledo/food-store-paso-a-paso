01 · Punto de partida

Lo que ya tenés en la mochila

La clase pasada instalaste jr-stack en tu agente. Eso te dejó tres piezas listas para usar: el orchestrator OPSX, memoria persistente con Engram y documentación al día con Context7. Más el OpenSpec CLI instalado a parte.

Hoy las usamos por primera vez en un proyecto real. Si por algún motivo no tenés OpenSpec, instalalo con npm install -g @fission-ai/openspec@latest · openspec.dev
Orchestrator OPSX Engram Context7

02 · Punto de partida

Clonar el repo base

Te damos un repositorio scaffolded: backend/, frontend/, docs/, .gitignore, README. No tiene código de negocio. Tiene la estructura para que arranques sin perder 20 minutos en decidir nombres de carpetas.

Lo que enseñamos hoy no es scaffolding — eso ya está. Lo que enseñamos es el proceso: cómo se piensa, planifica y construye un sistema con SDD.
git clone backend/ frontend/ docs/

03 · Conocimiento

Instalar las skills

Dos skills, una sola vez. find-skills de Vercel Labs te deja descubrir y agregar más sin salir del agente. kb-creator es la nuestra: convierte documentos fuente en una base de conocimiento estructurada.

Las skills viven en ~/.agents/skills/ y se symlinkean a cada agente, no en el repo. Se instalan una vez por máquina y quedan disponibles en Claude Code, Cursor, OpenCode y más.
npx skills add find-skills kb-creator

04 · Conocimiento

Generar la base de conocimiento

Tres documentos monolíticos en docs/ entran a la skill. Salen 10 archivos canónicos en knowledge-base/: visión, datos, reglas, flujos, arquitectura, decisiones, preguntas abiertas. La fuente es el documento — la KB es el contrato.

La KB es lo que el agente consulta antes de proponer cualquier cambio. Si algo no está acá, no existe para él. Una KB clara es lo que separa el SDD del vibe coding.

05 · Framework

Inicializar OpenSpec

Requisito: tener instalado el OpenSpec CLI (npm install -g @fission-ai/openspec@latest). Después, un comando crea la carpeta openspec/ donde van a vivir los specs y los changes, más las skills y commands del flujo OPSX adaptados a tu agente.

Le decimos qué agente vamos a usar — opencode, claude, ambos — y prepara las instrucciones. El agente reinicia y ya tiene /opsx:propose, /opsx:apply, /opsx:archive listos. Más info en openspec.dev.
openspec init openspec/ .claude/ .opencode/

06 · Framework

Configurar AGENTS.md

El archivo que el agente lee antes de cada acción no trivial. Stack, rutas, convenciones de naming, reglas duras, skills disponibles. Si la KB es qué construimos, AGENTS.md es cómo trabajamos.

Reglas duras que vale la pena dejar explícitas: no buildear automático, no commitear sin pedido, conventional commits sin Co-Authored-By, tests sin mocks de DB. Con esto, el agente deja de pelearse con vos.

07 · Framework

Trazar el roadmap

La skill roadmap-generator lee la KB, identifica las capacidades, infiere dependencias técnicas y emite openspec/roadmap.md: tabla de changes con orden, justificación, y sugerencia del primer change a ejecutar.

Acá no se escribe una sola línea de código. Se decide en qué orden implementar y por qué. Auth antes que recursos protegidos, modelo de datos antes que CRUD, integraciones externas al final.

08 · Cambio E2E

us-000-setup de punta a punta

El primer change del roadmap: infraestructura base. Tres comandos OPSX, tres etapas, un solo flujo. Acá se ve qué hace cada uno y qué deja en el repo.

En vivo, si el agente demora más de la cuenta, saltamos al tag pre-cocinado del paso correspondiente y mostramos el resultado. La narrativa no se rompe, el reloj tampoco.
/opsx:propose /opsx:apply /opsx:archive

09 · Cierre

Lo que se llevan

No se llevan código de Food Store — se llevan el método. Tres cosas: una forma de trabajar, dos skills reusables en cualquier proyecto, y el hábito de escribir specs antes de tocar el editor.

El siguiente paso es de ustedes. Tomen su propio proyecto, corran kb-creator, generen el roadmap, y propongan el primer change. El método se aprende usándolo.
